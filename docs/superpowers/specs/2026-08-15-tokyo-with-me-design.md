## 1. 이 문서가 하는 일

현재 `index.html`(1,320줄 단일 파일)에 3일 일정이 하드코딩돼 있다. 이번 여행은 4일이고, 디즈니는 랜드가 아니라 씨이며, 숙소·항공·동선이 전부 확정됐다. 콘텐츠만 갈아끼우는 걸로는 안 되고 구조를 바꿔야 한다.

이 문서는 (1) 확정된 여행 사실, (2) 4일 타임라인, (3) 앱의 새 데이터 구조와 화면 사양을 정의한다. 이 문서가 확정되면 구현 계획을 따로 만든다.

## 4. 현재 앱의 문제

1. **일정·지도 핀·맛집이 각각 따로 하드코딩돼 있다.** 한 장소의 시간을 바꾸면 3~4곳을 동시에 고쳐야 하고, 하나 빠뜨리면 일정 탭과 지도가 서로 다른 말을 한다.
2. **날짜가 `TRIP = 2026-07-10~12`로 박혀 있다.** 3일 구조라 4일이 안 들어간다.
3. **Day 2가 "시부야 코스 / 디즈니 코스" 분기 구조**(`d1s`/`d1d`)로 돼 있다. 이번엔 분기가 없고 4일이 각각 다른 날이므로 이 구조 자체가 불필요하다.
4. **디즈니랜드 기준**이다 (하트의 여왕 뷔페 등). 디즈니씨로 전면 교체 필요.
5. **상태가 저장되지 않는다.** 새로고침하면 체크가 날아간다.
6. **길안내 링크가 구글맵 검색어 방식**이라 엉뚱한 곳으로 가는 경우가 있다.

## 5. 새 구조 — 데이터 모델

### 원칙

**여행 전체를 하나의 데이터 객체로 만들고, 모든 화면은 거기서 그린다.** 장소 하나를 한 번만 적으면 일정 탭 · 지도 핀 · 맛집/카페 탭 · 길안내 링크가 전부 그 정의에서 파생된다.

**단일 HTML 파일을 유지한다.** GitHub Pages에 그대로 올라가고, 빌드 도구가 필요 없으며, **비행기와 지하철에서 인터넷 없이 열린다.** 해외여행 앱에서 오프라인 동작은 프레임워크보다 중요하다.

### 장소 (Place)

모든 지점의 단일 정의. 일정·지도·맛집·카페가 이걸 참조한다.

```js
{
  id: 'ginza-happo',
  name: '긴자 핫포',
  jp: '銀座八芳',
  kind: 'food',              // food | cafe | sight | shop | active | transit | hotel
  area: '긴자',
  lat: 35.xxxx, lng: 139.xxxx,
  desc: '해산물 뷔페. 타라바·즈와이 게 무한, 120분제',
  cost: '¥0,000~',           // 실제 요금은 예약 시 확정
  hours: '11:30–22:00 (L.I. 20:00)',
  tip: '토요일이라 예약 권장',
  links: { map: '<구글맵 좌표 기반 링크>', book: '<예약 링크>' }
}
```

좌표를 필수로 갖는다. 이것이 지도 핀, 길안내 링크, 카페 거리순 정렬의 공통 재료가 된다.

**길안내 링크는 검색어가 아니라 좌표 기반으로 생성한다.** 현재의 검색어 방식은 동명 업소로 잘못 연결될 수 있다.

### 일정 (Day / Slot)

```js
{
  date: '2026-09-12',
  label: 'Day 1',
  theme: '긴자 + 아사쿠사',
  slots: [
    { time: '13:50', placeId: 'candeo-shimbashi', type: 'checkin', note: '캐리어 보관' },
    { time: '14:30', placeId: 'ginza-happo', type: 'meal',
      transit: { mode: 'walk', min: 5 },
      alternatives: ['ginza-xxx', 'ginza-yyy'] },
    ...
  ]
}
```

- `transit`은 **이전 슬롯에서 이 슬롯으로 오는 방법**을 담는다 (도보/전철, 소요 분, 노선명).
- `alternatives`는 기존 "바꾸기" 기능의 후보군. 기존 UX를 유지한다.

### 상태 (State)

체크박스·선택·메모 등 사용자가 만드는 값. **모두 공유 동기화 대상**이다.

```js
{
  checks: { 'prep:passport:me': true, 'shop:donki:3': true },
  picks:  { 'd1-lunch': 'ginza-happo' },
  budget: [ { date, label, yen, payer } ],
  visited: { 'cafe-fuglen': true }
}
```

## 6. 화면 사양

하단 탭은 6개가 된다. 기존 5개 + **카페**.

### 6-1. 일정 (Schedule)

- **날짜 스위처가 4개**가 된다 (기존 3개 + 분기 구조 제거).
- **시간 축 타임라인**으로 바꾼다. 카드 나열이 아니라 시각이 왼쪽에 흐르고, **현재 시각 기준으로 "지금/다음" 슬롯이 강조된다.** 여행 중에는 오늘 날짜가 자동 선택된다.
- 각 슬롯 사이에 이동 수단·소요 시간이 들어간다.
- 슬롯마다 좌표 기반 길안내 버튼.
- 여행 전에는 D-day 카운트다운을 보여준다.

### 6-2. 디즈니씨 (Day 2 전용 화면)

일반 슬롯 카드로는 부족하다. Day 2를 선택하면 전용 레이아웃이 뜬다.

- **어트랙션 우선순위 리스트** — 둘이 미리 순위를 정하고 체크해나가는 형태. 16시 퇴장 전제이므로 "꼭 탈 것 / 되면 탈 것"으로 나눈다.
- **프리미어 액세스 / 얼리 엔트리 전략 메모**
- **쇼·퍼레이드 시간표**
- **파크 내 식사 후보**
- **퇴장 후 플랜** — 16:00 퇴장 → 유라쿠초 긴자 쇼핑 → 신바시 가드시타 간맥 → 도보 귀가. 이 흐름을 하단에 붙인다.
- 도쿄역 케이요선 도보 15분 경고를 이동 안내에 명시한다.

### 6-3. 카페 (신설)

- 동네별 카페를 큐레이션해서 넣는다 (긴자·아사쿠사·하라주쿠·오모테산도·시부야·신주쿠, 동네당 4~6곳).
- **브라우저 Geolocation으로 현재 위치를 읽어 거리순 정렬**한다. 외부 API를 쓰지 않으므로 무료이고 **오프라인에서도 동작한다.**
- 카드에 표시: 거리, 이름, 한 줄 설명, 영업시간, 가격대, 길안내 버튼, "가봤음" 체크.
- 위치 권한을 거부하면 동네별 목록으로 폴백한다.

**구글 Places API를 쓰지 않는 이유:** (1) public 레포라 API 키가 노출되고 결제수단 등록이 필수다. (2) 구글은 받아온 데이터 저장을 금지하므로 매번 실시간 호출이 필요하고, **네트워크가 끊기면 탭이 백지가 된다.** (3) 평점 정렬은 취향을 반영하지 못한다. 실시간 영업 여부만 포기하면 나머지는 API 없이 전부 구현된다. 각 카드의 구글맵 링크로 실시간 확인은 가능하다.

### 6-4. 맛집 (Food)

기존 구조 유지. 4일치로 재구성하고 디즈니씨 파크 내 식사로 교체한다. 카페는 이 탭에서 분리해 6-3으로 옮긴다.

### 6-5. 쇼핑 (Shop)

기존 카테고리(돈키호테 / 편의점 / 드럭스토어) 유지 + 항목 추가·체크가 **공유 동기화**된다. 긴자 쇼핑(Day 2 저녁)을 위한 매장 목록을 추가한다.

### 6-6. 준비물 (Prep)

**3박 4일 기준으로 다시 채운다.** 현재는 2박 3일 기준이다.

추가할 항목:
- **Visit Japan Web 사전등록** (입국 대기 단축, 첫날 30분을 좌우)
- **F45용** — 운동복, 운동화, 수건, 예약 확인
- **디즈니 종일 대비** — 보조배터리, 우비, 편한 신발
- 티웨이 수하물 규정 확인

**항목마다 담당자 표시**를 붙인다 (각자 / 나 / 애인). 여권처럼 각자 챙기는 것과 보조배터리처럼 한 명만 챙기면 되는 것을 구분한다.

### 6-7. 소통 (Phrase)

기존 카테고리·모달 구조 유지. 이번 일정에 맞는 상황을 추가한다.

- **F45 드롭인** — 예약 확인, 체험 수업 문의, 수건 대여
- **뷔페** — 인원, 제한 시간, 리필 가능 여부
- **디즈니씨** — 줄 확인, 대기 시간, 프리미어 액세스 구매처
- **면세** — 면세 가능 여부, 여권 제시

### 6-8. 예산 (Budget)

우선순위 낮음. 최소 형태로 만든다.

- 항목 입력 (날짜 / 내용 / 엔화 / 낸 사람)
- 일별·총합, 원화 환산 (환율은 수동 입력)
- 공유 동기화 대상

## 7. 공유 동기화

두 사람이 각자 폰에서 쓰고 서로 반영되게 한다.

- **Supabase**를 쓴다. 테이블 하나에 여행 상태를 담고, Realtime 구독으로 상대 변경을 수 초 내 반영한다.
- **로컬 우선(local-first)** 으로 동작한다. 모든 변경은 즉시 `localStorage`에 쓰고 화면에 반영한 뒤, 네트워크가 있을 때 서버로 보낸다. **지하철·파크 안에서 데이터가 끊겨도 체크가 사라지지 않는다.**
- 충돌은 **마지막 쓰기 우선(last-write-wins)** 으로 처리한다. 체크박스 위주라 이걸로 충분하다.
- **접근 코드 `1201`.** 앱 진입 시 1회 입력, 이후 기기에 기억한다. public 레포이므로 URL만으로 남이 상태를 바꾸는 것을 막는다.
- Supabase anon key는 공개돼도 되는 키이며, RLS로 접근을 제한한다.

---

## 8. 비기능 요건

- **오프라인 우선.** 지도 타일과 카페 실시간 정보를 제외한 모든 기능이 네트워크 없이 동작해야 한다.
- **모바일 우선.** 실제 사용 환경이 이동 중 한 손 조작이다. 미디어쿼리는 base 규칙 뒤에 배치한다.
- **단일 HTML 파일 유지**, 빌드 단계 없음, GitHub Pages 배포 유지.
- 외부 의존성은 Leaflet(지도)과 Supabase 클라이언트로 제한한다.
- 배포 전 인라인 JS를 `node --check`로 문법 검증한다.
